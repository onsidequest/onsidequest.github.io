## Motivation

- Most of today's AI systems remain bound by fixed, human-designed
  architectures, which tie the pace of progress to human intervention
- The original Gödel machine requires a formal proof that every self-modification is beneficial, which is impossible in practice. The DGM instead validates each change empirically on coding benchmarks

## What the paper wants to say

- Higher performance on coding benchmarks indicates better coding capability, and hence a better ability to self-modify and self-improve
- Greedily picking the best agent at each step of self-evolution can trap the system in a local optimum

## Findings

- Selecting appropriate criteria for measuring an agent's performance is critical for self-evolution
- Keeping an archive of diverse agents, including lower-performing ones, as stepping stones yields better results than always building on the best agent

## Method

![DGM overview]({{ '/assets/img/dgm/dgm-fig1.png' | relative_url }})
*Figure 1 of the paper.*

### Agent

- The agent receives a single input prompt that specifies the location of the target repository, the problem statement, and the repository's testing framework

### Evolution Strategy

![DGM archive tree]({{ '/assets/img/dgm/dgm-archive.png' | relative_url }})
*Figure 3 (left) of the paper. The archive of agents from the DGM run on SWE-bench.*

- In each iteration, the DGM selects parent agents to self-modify and branch off to produce new agents
  - Parent selection weight: $$w_i = \frac{1}{1 + e^{-\lambda(\alpha_i - \alpha_0)}} \times \frac{1}{1 + n_i}$$
  - $$\alpha_i$$ is the agent's performance score, $$n_i$$ is the number of its children with codebase-editing functionality, $$\lambda = 10$$ and $$\alpha_0 = 0.5$$
- The selected parent analyzes its own benchmark evaluation logs, proposes a new feature to implement, and receives this proposal as a problem statement to execute
- Each newly generated agent that compiles successfully is evaluated on the chosen coding benchmark and added to the DGM archive

### Experiment Setup

- SWE-bench and Polyglot are used to evaluate the DGM
  - SWE-bench has only Python tasks, while Polyglot has tasks in multiple programming languages
- The DGM runs for 80 iterations (one new agent per iteration), with two iterations running in parallel for SWE-bench and four for Polyglot
- A staged evaluation strategy estimates each coding agent's performance
  1. Evaluate on 10 tasks to verify basic codebase-editing functionality
  2. Evaluate on a set of 50 tasks
     - SWE-bench: SWE-bench-verified-mini
     - Polyglot: a random subset of the full benchmark
  3. Use the subset evaluations to estimate general effectiveness and identify top candidates
     - SWE-bench: an agent with over 40% success on the 60-task subset that ranks among the top two in the archive is evaluated on 200 tasks
     - Polyglot: an agent with over 40% success on the 10-task subset is evaluated on an expanded 50-task subset
